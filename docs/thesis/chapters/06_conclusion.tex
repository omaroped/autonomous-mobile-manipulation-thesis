\section{Summary of Contributions}
This thesis developed and validated a complete autonomous mobile manipulation pipeline
for a compact cobot platform (Agilex LIMO PRO + myCobot 280) operating in a
ROS~2-based simulation environment. The principal contributions are:

\begin{enumerate}
    \item \textbf{Verified simulation environment.} A Gazebo Classic simulation was
    constructed that mirrors the physical platform's kinematics, sensor placement, and
    coordinate frames. All physically meaningful parameters---wheel track, sensor fields
    of view, camera depth range, gripper clamping limits, and arm link geometry---were
    traced to manufacturer specifications and corrected where inherited models contained
    errors. The simulation is designed as the first phase of a sim-to-real workflow: the
    hardware-agnostic software layers (perception, planning, orchestration) are expected
    to transfer to the physical robot without modification.

    \item \textbf{Autonomous navigation pipeline.} A differential-drive navigation stack
    was integrated using Nav2 and SLAM Toolbox. A clean occupancy map of the workspace
    was built (238$\times$358 cells, 0.05\,m/cell, zero spurious obstacle cells) after
    correcting a LiDAR self-scan fault introduced by an excessively wide sensor field of
    view. Navigation costmap parameters were tuned to account for the arm's forward
    extent, which otherwise self-marks the robot's own vicinity as a lethal obstacle.

    \item \textbf{Perception pipeline.} Target object localisation is performed by an
    HSV-thresholded centroid detector on the RGB image combined with depth de-projection
    via the pinhole camera model, producing a 3D \texttt{PoseStamped} on
    \texttt{/box\_pose}. The pipeline is deliberately classical---no learning is
    required---to permit full diagnostic traceability for a single known-colour target.

    \item \textbf{MoveIt~2 arm control with reach characterisation.} The 6-DoF arm is
    planned with MoveIt~2 using a 22-seed KDL IK search and OMPL RRTConnect. The usable
    Cartesian workspace for a top-down grasp was characterised empirically: 25.9\,\%
    overall reachability in a 750-pose sweep, contracting sharply beyond
    $x\approx0.18$\,m, with side-approach orientations materially enlarging the usable
    envelope (290 versus 194 reachable poses in a 2025-pose comparative sweep).

    \item \textbf{Integrated navigation--manipulation orchestrator.} A single
    \texttt{nav\_pick\_orchestrator} node sequences the full task cycle---travel posture,
    navigation, visual docking, grasp, and backup---through a deterministic state machine
    that holds action clients for both Nav2 and MoveIt. An arm transport posture
    (\texttt{travel}) was identified and implemented to suppress inertial oscillation at
    the arm's horizontal-axis shoulder joint (joint~2) during base navigation. The
    grasp-weld service was corrected to use a live TF lookup at grasp time rather than a
    stale startup pose, enabling correct weld placement after the base has moved.

    \item \textbf{Engineering fault catalogue.} Twenty-nine distinct faults were
    identified, diagnosed, and resolved during the development cycle (Chapters~4 and~5).
    Several are of methodological significance beyond this specific platform: the LIDAR
    self-hit pattern, the MoveIt collision matrix incompleteness, the costmap obstacle
    range interaction with a mounted arm, the GPU PRIME offload requirement for
    depth-camera rendering on Optimus laptops, and the stale-pose failure mode in mobile
    manipulation weld services.
\end{enumerate}

\section{Addressing Research Objectives}
The research objectives stated in Chapter~1 are addressed as follows.

\textit{Objective 1: Design and implement an autonomous navigation pipeline for the
LIMO PRO platform in a simulated factory environment.}
Met. The robot navigates autonomously from any start position to a goal waypoint using
Nav2, AMCL localisation, and a pre-built SLAM map. The pipeline was validated by
commanding a sequence of goals throughout the simulated workspace without manual
intervention.

\textit{Objective 2: Integrate a perception system capable of localising a target
object in the robot's manipulation workspace.}
Met in simulation. The HSV + depth de-projection pipeline reliably produces a
\texttt{PoseStamped} on \texttt{/box\_pose} for a known-colour target within the arm's
reachable envelope. The sim-to-real gap introduced by the physical camera's 0.30\,m
blind spot is identified and quantified, and must be addressed in the hardware phase.

\textit{Objective 3: Execute a complete pick-and-place cycle combining autonomous
navigation and arm manipulation.}
Partially met. The navigate $\to$ dock $\to$ pick $\to$ backup cycle was demonstrated
in simulation. The place stage (depositing the object at a second location) has been
designed but not yet implemented; this constitutes the principal remaining task for the
integration phase.

\textit{Objective 4: Establish a quantitative sim-to-real baseline for the pipeline.}
Not yet met. All testing to date has been conducted in simulation under ideal odometry
(\texttt{odometry\_source: WORLD}). Hardware deployment and a comparative trial campaign
(success rate, final pose error, cycle time) against the physical LIMO and myCobot
platform is identified as the primary remaining research contribution.

\section{Limitations}
The following limitations are reported candidly, as each has material implications for
the interpretation of results.

\textbf{Ideal simulation odometry.} The simulation uses Gazebo's world-frame odometry
source, which provides drift-free, noise-free pose estimates. The navigation and
manipulation pipeline has not been validated under realistic odometry with cumulative
drift. Performance on the physical robot, where dead-reckoning errors accumulate, is
unknown at the time of writing.

\textbf{Single known-colour target.} The perception pipeline is specific to a single
target with a known HSV colour range. It does not generalise to arbitrary objects,
multiple targets, or targets that overlap in colour with the background. A learned
detector or more general geometric segmentation would be required for a production
scenario.

\textbf{Simulation attachment model.} Grasping in simulation is realised by rigidly
welding the object to the gripper link at grasp time. This bypasses the need for
sufficient friction and gripper force closure, which are the dominant failure modes of
real grasping. The weld model provides a correct structural test of the navigation,
perception, and planning layers but does not validate the physical grasp.

\textbf{Reachability constraint.} The effective top-down grasp reach of the myCobot
280 is materially shorter than the nominal 280\,mm arm length (see
Chapter~\ref{ch:experiments}). The platform's forward overhang, combined with the
camera's minimum depth range, defines a narrow feasible window that may require precise
stopping accuracy on the physical robot.

\textbf{Place stage not implemented.} The second half of the pick-and-place cycle---
transporting and depositing the object at a target location---is currently a stub.
The integrated pipeline therefore demonstrates only a subset of a full logistics task.

\section{Future Work}

\textbf{Place stage and box stacking.} Completing the place stage is the immediate
next engineering priority. The thesis direction is towards a multi-cycle stacking
scenario: the robot picks boxes from a source pile and stacks them vertically at a
target location. This scenario exercises the full pipeline repeatedly and provides
the statistical data needed for a sim-to-real drop-rate analysis.

\textbf{Sim-to-Real deployment.} Deploying the pipeline on the physical LIMO Cobot
platform is the principal remaining research contribution. This requires substituting
the Gazebo plugins with the real hardware drivers (Jetson Orin Nano, myCobot serial
interface, Orbbec DaBai driver), running a real SLAM session in the physical
laboratory, and conducting $N \ge 20$ pick-and-place trials to measure success rate,
final arm positioning error, and cycle time. Comparison of the simulation results
with the hardware results constitutes the sim-to-real evaluation.

\textbf{Odometry noise characterisation.} Replacing \texttt{odometry\_source: WORLD}
with real wheel encoder integration (or adding Gaussian noise to the simulation
odometry) will expose how much AMCL localisation quality degrades under realistic
drift, and quantify the impact on grasp success rate. This is a necessary precursor to
meaningful hardware trials.

\textbf{Side-approach grasp geometry.} The reachability analysis in Chapter~5
demonstrated that a side approach (arm oriented perpendicular to the base's forward
direction) increases the number of reachable grasp configurations compared to a pure
top-down approach. Implementing a side-approach sequence---navigate to the front of the
target, rotate 90° in place, then grasp from the robot's right flank---is a candidate
extension that could enlarge the operational workspace without any hardware modification.

\textbf{LiDAR-assisted object detection.} The current pipeline relies entirely on the
depth camera for object localisation. The LiDAR, used exclusively for navigation and
mapping, could in principle also detect the target object's bounding silhouette from a
standing range, providing a coarse initial estimate before the depth camera's close-range
de-projection. This would extend the detection range beyond the camera's 0.30\,m
physical minimum and improve approach targeting.

\textbf{Wrist yaw alignment.} The current grasp pipeline fixes the gripper roll
orientation and does not adjust it to the target box's yaw. For a box rotated away from
the gripper's default closing axis, the fingers will contact the box at an angle rather
than flat against its faces. Dynamically computing the optimal wrist yaw from the
box's detected orientation---and verifying IK feasibility---is a robustness improvement
that is particularly important for real scenes where box orientation is not controlled.

\textbf{Collision matrix refinement.} The simulation disables arm--base collision
checking due to coarse base mesh geometry (Section~4). Generating tighter collision
meshes for the base, sensors, and arm mount, and regenerating the SRDF collision matrix,
would permit arm--base checking to be re-enabled, improving planning safety on both
simulated and real hardware.
